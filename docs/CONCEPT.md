# Helix Orchestration — Concept

---

## What It Is

A distributed lab automation platform that coordinates fumehoods, devices, analytical instruments, workflows, trend data streams, and experiments.

Two operational tiers:

- **Local (Agent):** one agent per fumehood — execution, device control, safety
- **Site (Server):** aggregation, visibility, experiment registry, dashboards

The core runtime (`Helix.Orchestration.Core`) is headless, UI-agnostic, and transport-agnostic.

---

## Problem Statement

Lab automation requires:

- Long-running workflows that survive crashes and restarts
- Coordinating instruments across incompatible protocols (OPC UA, SiLA 2, SDKs, serial, file-drop)
- Real-time sensor trends driving dynamic workflow logic (stability, thresholds, slopes)
- PAT-grade online spectroscopy (MIR, UV/Vis, NIR, Raman) with per-scan x/y array data
- Online Diode Array (DAD/PDA) producing time-evolving 2D spectral matrices
- Image and video capture from cameras and microscopes
- Offline analytics results (scalar, string, integer, structured) correlated to experiments
- Derived trends computed via mathematical expressions or Python scripts
- Declarative WSL workflows generated by UI/chatbot/ELN/ML systems
- Multi-experiment Campaign orchestration for optimisation, DoE, and sweeps
- Per-runspace device leasing with local safety enforcement
- All data and results traceable to a named experiment
- Safety enforcement that does not depend on network connectivity

## Design Principles

| Principle | Constraint |
|---|---|
| Device-agnostic | Workflows call capability names, not devices or protocols |
| Local execution | Workflow runs inside the agent — low latency, safe, resilient |
| Control vs. data separation | Control: gRPC/REST. Trends: MQTT/NATS. Binary: object storage |
| Experiment-centric | Every action, trend, file, result tagged with `ExperimentId` |
| Safety independence | Safety enforced locally — no network required |
| Authoring vs execution | WSL is authoring input; `RunspaceDefinition` is execution contract |
| Campaign isolation | Campaigns are Site Server-owned; agents only execute experiments |
| Runspace isolation | One runspace = one workflow instance + one context + one lease scope |
| Interface-first | Every subsystem boundary is an interface; backends are swappable |
| Single DI surface | `WorkflowContext` is the only dependency injected into a workflow |

## Site Server

Responsibilities:
- Registry of sites, fumehoods, agents, devices
- WSL ingestion and workflow compilation (`WSL` → `RunspaceDefinition`)
- Campaign management for multi-experiment orchestration
- Experiment tracking and status
- Subscribe to MQTT/NATS from all agents
- REST/gRPC API for UI, ELN/LIMS, chatbot, ML optimiser, analytics
- WebSocket event hub for live workflow/node updates
- Dashboards: device status, experiment history, analytical queues

Not responsible for: direct device control, local safety enforcement, per-step workflow execution.

| Component | Technology |
|---|---|
| Runtime | .NET 8 ASP.NET service |
| Workflow contract | WSL (JSON declarative) |
| Compiler output | `RunspaceDefinition` JSON |
| Campaign state | Site-owned persistent orchestration state |
| Database | PostgreSQL / SQLite |
| Telemetry | MQTT/NATS subscriber |
| Binary storage | S3 / Blob / MinIO |
| Agent comms | gRPC + REST |
| Realtime events | WebSockets/SignalR |

## Fumehood Agent

Responsibilities:
- Host device adapters
- Execute compiled `RunspaceDefinition` workflows in Runspaces
- Maintain one `ExperimentContext` or `TestContext` per runspace
- Enforce local safety rules
- Stream trends via MQTT/NATS
- Handle binary data (chromatograms, spectra, images)
- Perform device leasing (exclusive/shared)
- Support simulation mode when hardware is unavailable

| Component | Technology |

| Execution abstraction | Helix Runspace |
| Durable execution | Cleipnir.ResilientFunctions |
| Messaging | MQTT/NATS client |
| Site comms | gRPC server + REST callbacks |
| Local state | SQLite |
| Drivers | Plugin system — language-agnostic |

## Device Adapters and Capabilities

Each device has an adapter translating its vendor protocol into named capability verbs.

| Device | Protocol | Adapter |
|---|---|---|
| Reactor | OPC UA | C# |
| Pump | Modbus/serial | Python or C# |
| Agilent HPLC | ICF + file-drop | C# + file watcher |
| Camera | SDK / RTSP | Node.js or C# |
| Spectrometer | Vendor SDK | Python |

Capability verbs exposed by adapters:

```
SetTemperature  GetPressure  RunMethod  AcquireSpectrum  CaptureImage
```

Workflow code never sees a protocol. It only calls:

```csharp
await ctx.Capabilities.InvokeAsync("SetTemperature", new { Value = 75 });
```

## Data Model

### Trends — stratified data model

All trend kinds share a common `ITrend` identity (id, name, kind, units, experiment tag, online/offline flag). Data shape varies by kind:

| Kind | Shape | Examples |
|---|---|---|
| `Scalar` | single `double` / `int` / `string` / `bool` | Temperature, pressure, flow, pH |
| `Spectral` | `xData[]` + `yData[]` per scan | MIR, UV/Vis, NIR, Raman |
| `DiodeArray` | `wavelengths[]` × time slices (2D) | Online DAD/PDA chromatography |
| `Image` | binary reference + metadata | Camera frames, microscope images |
| `Video` | streaming binary segments | Reaction video capture |
| `AnalyticsResult` | structured result object | Offline peak area, concentration |
| `Derived` | computed from ≥1 source trends | Math expressions, Python scripts |

All kinds publish updates as `IObservable<TrendValue>` streams.

`TrendValue` is a discriminated union of:
- `Scalar<T>` — typed numeric or string value
- `DoubleArray` — paired x/y arrays (spectral data)
- `Spectral` — full `SpectralScan` record
- `Image` — `ImageFrame` with storage URI
- `StructuredResult` — named result type + arbitrary object

### Scalar telemetry
- Temperature, pressure, flow, pH, etc.
- Published agent → MQTT/NATS → site + workflows + safety engine
- Backed by `TrendWindow<T>` circular buffer; queryable via `TrendFunctions`

### Spectral trends (MIR / UV / NIR / Raman)
- Each scan is a `SpectralScan`: `xData[]` (wavenumbers cm⁻¹ or wavelengths nm) + `yData[]` (absorbance or intensity)
- Rolling window of recent scans; subscribable via `IObservable<SpectralScan>`
- Spectral type encoded: `MIR | UV | NIR | Raman | Fluorescence`

### Diode Array (DAD/PDA) — online 2D chromatography
- Continuous stream of `DiodeArraySlice` objects (one absorbance value per wavelength per time point)
- Full 2D matrix (`wavelength × time`) available as a rolling window snapshot
- Single-wavelength chromatogram extractable as a `IScalarTrend<double>`
- Single-timepoint spectrum extractable as a `SpectralScan`

### Binary data — images and video
- Binary payload stored in S3 / Blob / MinIO; trend holds storage URI + metadata
- MQTT carries: metadata, file pointers, event notifications (not the binary payload)
- `IImageTrend` streams `ImageFrame` records (inline thumbnail optional)
- `IVideoTrend` streams `VideoSegment` references

### Derived trends
- Pure functions over ≥1 source trends; evaluated eagerly, lazily, or on cadence
- Three derivation modes: `MathExpression` (NCalc/MathNet), `PythonScript` (via `IPythonTrendEvaluator`), `CSharpDelegate`
- Source trend ids are declared; dependency graph is tracked by `ITrendProvider`

### Offline analytics results
- Pushed into the trend system by the analytics engine after a run completes (event-driven)
- Arrive as `AnalyticsResult` trend values; correlated to experiment via `ExperimentId`
- Scalar results, string results, integers, and structured objects all supported

### Experiment context — every data point is tagged
```
ExperimentId  SiteId  FumehoodId  DeviceId  Timestamp  Method  Operator
```

## WSL (Workflow Specification Language)

WSL is a neutral, declarative, JSON-based workflow format.
It defines what a workflow should do, not how execution is implemented.

WSL is the contract between Node-Flow UI, chatbot, ELN/LIMS, Site Server, Agents, and ML optimisation services.

### WSL structure

- `version`, `name`, `mode`
- `nodes[]` containing declarative step definitions
- `edges[]` defining sequencing/branching/loopback
- Logical `device` references resolved by Site Server Device Registry
- Optional embedded safety envelope constraints

### Authoring and execution flow

```
WSL (JSON)
   ↓
Workflow Compiler (Site Server)
   ↓
RunspaceDefinition (JSON)
   ↓
Agent Runspace Execution
```

### WSL generation rules for LLMs

- Valid JSON only
- Declarative intent only (no imperative code)
- Node type maps to known workflow primitive
- Device uses logical device names
- Parameters conform to capability schema
- Edges reference valid node ids

## Campaign Manager (Site-only)

A Campaign is a high-level orchestration unit for multi-experiment autonomous runs.
Campaigns live only in the Site Server.
Agents never own campaign state.

### Campaign examples

- Multi-iteration CSTR tuning
- Design-of-Experiments parameter grids
- ML-driven flow chemistry optimisation loops
- Multi-stage continuous process optimisation

### Separation rule

- **Site Server Campaign Manager:** owns campaign lifecycle, chooses next experiment, updates optimiser, decides stop criteria
- **Agent:** executes one experiment/runspace, streams telemetry, reports results, releases leases

This keeps campaign state centralized, auditable, and crash-safe.

---

## Runspace

A Runspace is a Helix execution container for one workflow instance.
It is not a Cleipnir primitive, AppDomain, or AssemblyLoadContext.

### Runspace contents

- Execution state machine (current node, branches, loops, waits)
- One `ExperimentContext` or `TestContext`
- Device leases
- Trend subscriptions and safety envelope state
- Durable continuation state persisted via Cleipnir

### Relationship to Cleipnir

- Cleipnir provides durability and resumability
- Runspace provides Helix semantics (capabilities, trends, safety, leasing, context)

## Core Runtime Subsystems

### 1. Workflow Engine
- `IWorkflow` — `ExecuteAsync(WorkflowContext, CancellationToken)`
- `WorkflowContext` — carries Capabilities, Trends, Safety, State, Experiment
- `WorkflowRegistry` — name to implementation lookup

### 2. Execution Engine
- `WorkflowExecutor` — Cleipnir `FunctionsRegistry` + `ActionRegistration<T>` for crash-safe invocation
- Primitives: `WorkflowStep`, `Condition`, `Branch`, `Loop`, `ParallelBlock`, `Delay`, `WaitFor`, `RetryPolicy`

### 3. State Persistence
- `WorkflowState` — serialisable: status, variables, logs, experiment reference
- `IWorkflowStateStore` — save / get / delete / list
- Current: in-memory. Production: Cleipnir PostgreSQL store

### 4. Capability Invocation
- `ICapabilityInvoker` — `InvokeAsync(name, params)` / `IsAvailableAsync(name)`
- `CapabilityRegistry` — dispatches to registered adapters by capability name

### 5. Trend Integration

A stratified model where all trend kinds share a common `ITrend` root and a `TrendKind` discriminator.

**Core interfaces:**
- `ITrend` — identity: `TrendId`, `TrendName`, `TrendKind`, `Units`, `ExperimentId`, `Tags`, `IsOnline`
- `IScalarTrend<T>` — backed by `TrendWindow<T>` circular buffer; `TrendFunctions` operate on it
- `ISpectralTrend` — rolling window of `SpectralScan` records; `IObservable<SpectralScan>` stream
- `IDiodeArrayTrend` — 2D DAD/PDA matrix; slice stream; chromatogram + spectrum extraction
- `IImageTrend` — `IObservable<ImageFrame>` stream; binary referenced via storage URI
- `IVideoTrend` — `IObservable<VideoSegment>` stream
- `IDerivedTrend` — declares source trend ids and `DerivationKind`
- `ITrendProvider` — typed accessors for each kind, trend discovery by kind/experiment, derived trend registration

**Value type:**
- `TrendValue` — discriminated union: `Scalar<T>`, `DoubleArray`, `Spectral`, `Image`, `StructuredResult`

**Derivation modes:**
- `MathExpression` — expression string evaluated against named source values (e.g. `"peak_area / uv_baseline"`)
- `PythonScript` — delegated to `IPythonTrendEvaluator`; receives input dictionary, returns `TrendValue`
- `CSharpDelegate` — inline `Func<IReadOnlyDictionary<string, TrendValue>, TrendValue>`

**Scalar usage (unchanged):**

```csharp
while (!TrendFunctions.IsStable(ctx.Trends.GetScalarTrend<double>("reactor.temp")))
    await Task.Delay(TimeSpan.FromSeconds(5), ct);
```

**Spectral usage:**

```csharp
var mir = ctx.Trends.GetSpectralTrend("mir.reactor");
var latestScan = mir.LatestScan;  // SpectralScan with XData (cm⁻¹) and YData (Abs)
```

**Derived trend registration:**

```csharp
ctx.Trends.RegisterDerivedTrend(new DerivedTrendDefinition(
    TrendId: "carbonyl_norm",
    DerivationKind: DerivationKind.MathExpression,
    Expression: "peak_area / uv_baseline",
    SourceTrendIds: ["mir.peak_1750", "uv.baseline"]));
```

### 6. Safety Engine
- `InterlockRule` — async predicate with `RuleId`, `Description`, `Severity`
- `SafetyEngine` — evaluates rules, triggers emergency stop on critical violations
- `EmergencyStopToken` — `CancellationToken` broadcast to all running workflows
- Background monitoring loop via `StartInterlockMonitoringAsync`

### 7. Experiment Context
- `ExperimentLifecycle`: `Created → Running → Suspended → Completed / Failed`
- `IExperimentContext` — lifecycle transitions, metadata, data recording
- Full traceability of measurements and results back to `ExperimentId`

### 8. WSL Contract and Compiler
- WSL JSON schema validation and semantic checks
- Device binding resolution against logical Device Registry
- Compiler output as `RunspaceDefinition`

### 9. Campaign Manager (Site Server)
- Campaign lifecycle, iteration strategy, and stop criteria
- Multi-experiment orchestration and result aggregation
- ML optimiser loop integration

### 10. Runspace Engine (Agent)
- One runspace per workflow instance
- Context lifecycle (`ExperimentContext` / `TestContext`)
- Capability interpreter for compiled `RunspaceDefinition`

### 11. Device Leasing Service
- Exclusive/shared lease acquisition and release
- Lease timeout and heartbeat-driven reclamation
- Safety-aware preemption rules

## Execution Flow

```
WSL authoring source (UI / Chatbot / ELN / ML)
        │
        ▼
Site Server Workflow Compiler
        │
        ├── Validate WSL schema + node graph
        ├── Resolve logical devices via Device Registry
        ├── Inject/merge safety envelope constraints
        ├── Emit RunspaceDefinition
        │
        ▼
Agent Runspace Engine
        │
        ├── Acquire device leases
        ├── Create ExperimentContext or TestContext
        ├── Execute capabilities + trend conditions
        ├── Persist continuation via Cleipnir
        │
        ▼
Runspace completes / suspends / fails
```

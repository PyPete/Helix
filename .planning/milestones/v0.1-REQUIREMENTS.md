# Requirements

**Project:** Helix Orchestration Platform
**Scope:** Milestone 1 — Hardware-ready platform with local UI, full test coverage, documentation, and deployment scripts
**Status:** Active
**Last updated:** 2026-05-26

---

## Vision

A scientist or technician can build a visual workflow, connect real lab hardware (reactors, pumps, HPLC, spectrometers), execute an automated experiment, and see live results — all without writing code.

---

## User Stories

### Scientist — Workflow Authoring

- As a scientist, I can open the local fumehood desktop app and visually build a workflow using a node-flow editor, so I can design experiments without writing JSON or code.
- As a scientist, I can connect workflow nodes to logical device capability names (e.g. SetTemperature, RunMethod) and see which physical devices are available, so I can author protocol-correct workflows.
- As a scientist, I can save, version, and reload workflows between sessions, so my experiment designs are preserved.

### Scientist — Experiment Execution

- As a scientist, I can submit a workflow for execution and see real-time status of each workflow step, so I know exactly what the system is doing.
- As a scientist, I can monitor live trend data (temperature, pressure, flow, UV absorbance) in charts during execution, so I can intervene if the reaction deviates.
- As a scientist, I can see safety interlock status and know that the system will emergency-stop if a limit is violated, so I can trust the platform with real chemistry.

### Technician / Operator

- As a technician, I can launch a pre-built workflow and monitor equipment status without needing to understand the workflow definition, so I can run routine experiments.
- As a technician, I can view device connection status and see which adapters are healthy or faulted, so I can diagnose hardware issues quickly.
- As a technician, I can use the desktop app without a network connection to a Site Server, so the fumehood operates independently if the site network is unavailable.

### Site Operations

- As a site manager, I can view all fumehoods on a web dashboard, see which are running experiments and which are idle, so I have site-wide visibility.
- As a site manager, I can view experiment history, campaign status, and result summaries from the site dashboard, so I can report on lab utilisation.

### Developer / Integrator

- As a developer, I can implement a new device driver by extending DeviceAdapterBase and injecting the appropriate transport, so I can add new instruments without modifying the core platform.
- As a developer, I can read the Docusaurus documentation to understand the architecture and write adapter code, so I can onboard without needing to read all 14 phase handover docs.

## Non-Functional Requirements

| Category | Requirement |
|----------|-------------|
| Safety independence | Safety engine evaluates locally — never requires network connectivity |
| Standalone operation | Local Tauri UI must function with only Agent available (no Site Server) |
| Cross-platform | Tauri app: Windows 11 + Linux Debian/Ubuntu |
| Protocol fidelity | Device drivers must exactly reproduce POP.DeviceCore command vocabularies |
| Durability | Runspace state survives Agent process restart (PostgreSQL-backed Cleipnir) |
| Security (dev) | Default dev credentials (MinIO, Postgres) are acceptable for local dev; production requires TLS + credential rotation |

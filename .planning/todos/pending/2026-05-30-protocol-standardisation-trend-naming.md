## Problem

Without a formalised protocol model, experiment records are ambiguous: there is no machine-readable distinction between "what was planned" and "what actually ran", making QC, audit trails, and automation summaries unreliable. Separately, ad-hoc trend names (currently unvalidated strings) create silent mismatches between the Agent, UI, trend engines, and optimisation loops — a trend named `"temp"` in a Python script and `"temperature"` in the WSL step are treated as different series with no warning.

## Solution

Two complementary contracts: a **protocol standardisation model** that structures experiment records, and a **trend naming convention** that makes names stable and machine-safe across all subsystems.

## Part 1: Protocol Standardisation Model

### Planned Protocol vs. Event Protocol

Every experiment has two protocol documents:

| Document | Created when | Content | Purpose |
|---|---|---|---|
| **Planned Protocol** | At compile time (POST /workflows/compile) | The WSL workflow as authored: steps, parameters, control flow, expected devices | Blueprint — what was intended |
| **Event Protocol** | During / after execution | Timestamped record of what actually ran: step starts, completions, faults, parameter values actually used, trend snapshots | Execution trace — what happened |

The **automation summary** is generated by comparing Planned vs. Event Protocol: which steps ran, which were skipped, which faulted, what values differed from the plan.

### Protocol Schema

A **Protocol Schema** defines what is allowed in a workflow for a given experiment type. It is separate from WSL syntax validity (which the compiler already checks) — it enforces scientific/regulatory constraints.

```json
{
  "schemaId": "flow-chemistry-screen-v2",
  "description": "Flow chemistry screening protocol",
  "allowedSteps": [
    { "capability": "vapourtec_r4.set_temperature", "required": true, "units": "°C", "range": [20, 150] },
    { "capability": "vapourtec_r4.set_flow", "required": true, "units": "mL/min", "range": [0.1, 10.0] },
    { "capability": "knauer_azura.inject", "required": false },
    { "capability": "delay", "required": false }
  ],
  "allowedControlFlow": ["loop", "branch"],
  "requiredMetadata": ["operator", "project_code", "sample_id"],
  "requiredDevices": ["vapourtec_r4", "knauer_azura"],
  "maxLoopIterations": 100
}
```

**Schema enforcement points:**
- `POST /workflows/compile` with a `schemaId` → compiler validates the document against the schema; returns schema violations as `HTTP 422` diagnostics alongside WSL syntax errors
- Schema validation is **additive** — a document can be WSL-valid but schema-invalid (e.g. missing required metadata, step outside allowed range)
- Schemas are optional: a workflow compiled without a `schemaId` skips schema validation

**Control-flow constructs (loops and branches):**
- Permitted when the schema's `allowedControlFlow` list includes them
- Loop expansion (Phase 6 06-03) unrolls loops in the `RunspaceDefinition` for execution; the **Planned Protocol retains the unexpanded loop** for audit readability
- The Event Protocol records each loop iteration separately with its actual index and parameters

### Planned Protocol Document

Stored alongside the `RunspaceDefinition` at runspace creation time. Contains:

```json
{
  "protocolId": "run-2026-05-30-001",
  "schemaId": "flow-chemistry-screen-v2",
  "plannedAt": "2026-05-30T09:00:00Z",
  "operator": "Dr Smith",
  "projectCode": "HEL-042",
  "workflow": { /* WslDocument as authored, with loops intact */ },
  "expectedDevices": ["vapourtec_r4", "knauer_azura"],
  "expectedTrends": ["vapourtec_r4.temperature.pv", "knauer_azura.pressure.pv"]
}
```

### Event Protocol Document

Built incrementally during execution from `RunspaceEvent` frames. Completed at runspace termination. Contains:

```json
{
  "protocolId": "run-2026-05-30-001",
  "runspaceId": "rs-abc123",
  "startedAt": "2026-05-30T09:01:12Z",
  "completedAt": "2026-05-30T10:14:03Z",
  "outcome": "completed",
  "steps": [
    {
      "stepId": "heat",
      "capability": "vapourtec_r4.set_temperature",
      "plannedValue": 80,
      "actualValue": 80,
      "startedAt": "...",
      "completedAt": "...",
      "durationMs": 312000,
      "outcome": "completed"
    }
  ],
  "faults": [],
  "trendSnapshots": {
    "vapourtec_r4.temperature.pv": { "mean": 79.8, "stddev": 0.4, "min": 78.1, "max": 81.2 }
  }
}
```

### Automation Summary

Generated by `EventProtocolService.Compare(planned, event)`:

```
Protocol: flow-chemistry-screen-v2
Run: run-2026-05-30-001

Steps: 4/4 completed (0 faults)
Parameter deviations:
  - heat.set_temperature: planned 80°C, actual mean 79.8°C (±0.4°C) ✓ within tolerance
Loop iterations: 3 (planned 3) ✓

Devices used: vapourtec_r4 ✓, knauer_azura ✓
Trends recorded: 4/4 expected ✓

Result: PASS — all planned steps completed within tolerance
```

The summary is attached to the `ExperimentContext` and stored in the Recorder pipeline.

## Part 2: Trend Naming Convention

### Naming Rules

All trend names are **lowercase, dot-separated or slash-separated, machine-safe identifiers**.

**Raw device trends** — source is a physical device measurement:
```
<deviceId>.<capability>.<parameter>
```
Examples:
- `vapourtec_r4.temperature.pv`  (process value)
- `vapourtec_r4.temperature.sp`  (setpoint)
- `vapourtec_r4.flow.pv`
- `knauer_azura.pressure.pv`
- `uv_detector.absorbance.280nm`

Rules:
- `deviceId` matches the adapter registration name in `CapabilityRegistry`
- `capability` matches the registered capability verb name
- `parameter` is defined by the device driver (e.g. `pv`, `sp`, `flow`, `pressure`, `absorbance_Xnm`)
- Dots only (no slashes in raw trends)

**Derived trends** — computed by Local Engine or Python Sidecar:
```
<namespace>/<trendName>
```

| Namespace | Source | Examples |
|---|---|---|
| `custom` | User-defined Local Engine expression | `custom/conversion_rate`, `custom/temperature_delta` |
| `python` | Python Sidecar script | `python/pls_concentration`, `python/uv_pca_score1` |
| `system` | Agent built-in (moving average, rate-of-change) | `system/vapourtec_r4.temperature.pv.mavg5` |
| `optim` | Optimisation loop output (Ax/BoTorch) | `optim/yield_prediction`, `optim/acquisition_score` |

Rules:
- Namespace prefix is mandatory for all derived trends
- `trendName` within namespace: lowercase, underscores only (no dots, no spaces)
- Full name must be globally unique across all namespaces (the registry enforces this)

### Name Validation

Applied at trend definition registration time (`POST /trends` or file load):

```
Valid:   vapourtec_r4.temperature.pv
Valid:   custom/conversion_rate
Valid:   python/pls_concentration
Valid:   system/vapourtec_r4.temperature.pv.mavg5

Invalid: Temperature PV           (spaces, capital)
Invalid: custom.conversion_rate   (dot instead of slash in derived namespace)
Invalid: vapourtec/temperature/pv (slash in raw trend)
Invalid: custom/conversion rate   (space)
Invalid: PYTHON/model_output      (uppercase namespace)
```

Validation regex (raw): `^[a-z0-9_]+\.[a-z0-9_]+\.[a-z0-9_.]+$`
Validation regex (derived): `^(custom|python|system|optim)/[a-z0-9_]+$`

### Unified Trend Registry

All trends (raw + derived) are registered in a single `TrendRegistry` on the Agent:

```csharp
public record TrendDescriptor(
    string Name,           // validated full name
    TrendSource Source,    // Raw | LocalEngine | PythonSidecar | System
    string? DeviceId,      // for Raw trends
    string? Expression,    // for LocalEngine trends
    string? ScriptId,      // for PythonSidecar trends
    string Unit,
    TrendStatus Status     // Active | Stale | Degraded | Unavailable
);
```

`GET /trends` returns all registered trends with their current status. This is the single source of truth for the UI's trend browser, the WebSocket subscription filter, and the optimisation loop's result consumer.

### Name Stability Contract

Once a trend is registered with a given name, that name **must not change**:
- Recorder MQTT topics use the trend name as the topic suffix → renaming breaks historical data queries
- Workflow `WaitFor` steps reference trend names → renaming invalidates saved workflows
- Python optimisation loops reference trend names → renaming silently breaks result collection

**Rename procedure (when required):**
1. Register the new name as an alias pointing to the old series
2. Mark the old name as `deprecated` (still evaluates, logs a warning per use)
3. After a migration period, remove the deprecated name

This mirrors the principle used in database column migrations — never destructive rename, always alias first.

## Implementation hints

**Protocol model (Agent + Core):**
- `PlannedProtocol` record: stored at `POST /runspaces` time alongside `RunspaceDefinition`
- `EventProtocol` record: built incrementally from `RunspaceEvent` frames in `DurableRunspace`
- `EventProtocolService.Compare()`: pure function, no I/O
- Protocol schema: JSON Schema or a custom `ProtocolSchema` DSL; stored in `schemas/` directory
- `WslCompiler.Compile()`: extend signature with optional `ProtocolSchema?` parameter (alongside existing `ISafetyEngine?`)
- `POST /workflows/compile`: accept optional `schemaId` query param; load schema and pass to compiler

**Trend naming (Agent + TrendAggregator):**
- `TrendNameValidator.Validate(name)`: pure static method, no I/O; called at registration
- `TrendRegistry`: replaces the current ad-hoc string-keyed dictionaries in `TrendAggregator`
- `GET /trends`: new endpoint returning `TrendDescriptor[]`; grouped by namespace in response
- Rename/alias procedure: `POST /trends/{name}/alias` → `{ "newName": "..." }`

**Frontend:**
- Trend browser component: lists `GET /trends` response, grouped by namespace tabs (raw | custom | python | system | optim)
- Trend name validation in custom trend definition UI (live validation as user types)
- Protocol summary view: compare Planned vs. Event Protocol in a diff-style display

## Bug Analysis

### Bug 1 — G2/E3: docker-compose.yml missing ConnectionStrings__HelixOrchestration for helix-siteserver

**Root cause (verified by direct file read):**

`docker-compose.yml` `helix-siteserver` environment block (lines 105–112):

```yaml
environment:
  ASPNETCORE_URLS: http://+:5090
  AgentProxy__Mode: grpc
  AgentProxy__GrpcAddress: http://helix-agent:5080
  MqttBridge__BrokerHost: helix-mosquitto
  MqttBridge__BrokerPort: 1883
  MqttBridge__SiteId: site1
  MqttBridge__FumehoodId: fh1
```

`ConnectionStrings__HelixOrchestration` is absent. `helix-agent` has it (line 83). SiteServer does not.

**Why SiteServer crashes:** `SiteServer/Program.cs` calls `builder.Services.AddHelixInfrastructure(builder.Configuration)`. `AddHelixInfrastructure` is the same method used by Agent — it reads `ConnectionStrings["HelixOrchestration"]` and creates Npgsql connections. When the env var is missing in the container, EF Core / Npgsql throws at startup.

**Postgres service details (confirmed from docker-compose.yml):**
- Service name: `postgres`
- DB: `helix_orchestration`
- User: `helix`
- Password: `helix_dev_password`
- DNS alias inside Docker network: `helix-postgres` (set by `container_name`)

**Exact value to add:**
```
ConnectionStrings__HelixOrchestration: Host=helix-postgres;Port=5432;Database=helix_orchestration;Username=helix;Password=helix_dev_password
```
This is identical to the Agent's value on line 83.

**Files to change:**
- `docker-compose.yml` — add one line to `helix-siteserver.environment`

**Additional dependency required:**
SiteServer's `depends_on` block does not include `postgres`. After adding the connection string it will attempt to connect to postgres on startup, so `postgres` must be added to `helix-siteserver.depends_on`:
```yaml
depends_on:
  helix-agent:
    condition: service_healthy
  mosquitto:
    condition: service_healthy
  postgres:
    condition: service_started
```
(Agent already depends on postgres, so postgres will be running before SiteServer ever starts in the current dependency chain — but explicit declaration is safer and self-documenting.)

**Risk:** LOW. One env var addition + one depends_on entry. No code changes. Idempotent.

### Bug 2 — D5/D6: helix-desktop unit tests not in CI

**Root cause (verified by direct file read):**

`ci.yml` `tauri-build` job (lines 158–250): installs frontend deps (`npm ci`) and runs `npm run tauri build` only. No `npm test` step.

**helix-desktop test infrastructure confirmed:**
- `package.json` test script: `"test": "vitest"` (line 11)
- `vitest.config.ts` environment: `jsdom`, setupFiles: `./src/test/setup.ts`
- 76 tests exist (confirmed by audit: all pass locally)

**CI has a separate `dashboard` job (lines 91–116)** that already runs `npm test -- --run` for `helix-dashboard/`. The same pattern needs to be added for `helix-desktop/`.

**Exact fix — add a `helix-desktop-test` job to `ci.yml`:**

```yaml
helix-desktop-test:
  name: helix-desktop Tests
  runs-on: ubuntu-latest

  steps:
    - name: Checkout
      uses: actions/checkout@v4

    - name: Setup Node.js
      uses: actions/setup-node@v4
      with:
        node-version: 20
        cache: npm
        cache-dependency-path: helix-desktop/package-lock.json

    - name: Install dependencies
      working-directory: helix-desktop
      run: npm ci

    - name: Run tests
      working-directory: helix-desktop
      run: npm test -- --run
```

**Why `-- --run` is required:** `vitest` in watch mode blocks CI. `--run` makes it exit after one pass. This is already the pattern used by `helix-dashboard` job (line 112).

**Why a separate job (not a step in tauri-build):** The `tauri-build` job is a matrix job running on linux, macOS, and windows. Tests only need to run once (on ubuntu-latest). Adding a test step to the matrix would run tests 3× (wasted time) and also require all system dependencies (libwebkit2gtk, etc.) before tests run — an unnecessary coupling. A separate `helix-desktop-test` job mirrors the existing `dashboard` job pattern exactly.

**Does helix-desktop need system deps for tests?** No. Vitest runs in jsdom (Node.js, no browser). The system dependencies (libwebkit2gtk etc.) are only needed for `npm run tauri build`. The test job skips all Tauri/Rust setup.

**Files to change:**
- `.github/workflows/ci.yml` — add `helix-desktop-test` job (~20 lines)

**Risk:** LOW. Pure CI config addition. Tests already pass locally. If any test is environment-sensitive, the job will fail and surface the issue — which is the desired behaviour.

### Bug 3 — E4: Agent has no gRPC server

**Root cause (verified by direct file reads):**

1. `Helix.Orchestration.Agent/gRPC/Server/` — directory exists but contains **zero files** (glob returned no results).
2. `Agent/Program.cs` — no `AddGrpc()` call, no `MapGrpcService<>()` call, no gRPC-related `using` imports.
3. `Agent.csproj` has `Grpc.AspNetCore Version="2.*"` already referenced (line 13) and also has `Grpc.Net.Client Version="2.*"` (line 14). **The NuGet package is already present — no new package install needed.**
4. `Helix.Orchestration.Contracts.csproj` includes `Protos\agent_control.proto` with `GrpcServices="Both"` — this generates both server-side base class (`AgentControlBase`) and client-side stubs. The generated server base class is already available.

**What the proto defines (agent_control.proto):**

Service `AgentControl` with 5 RPCs:
- `SubmitExperiment(ExperimentSubmission) → SubmissionAck`
- `PauseRunspace(RunspaceCommand) → CommandAck`
- `ResumeRunspace(RunspaceCommand) → CommandAck`
- `AbortRunspace(RunspaceCommand) → CommandAck`
- `GetRunspaceStatus(RunspaceQuery) → RunspaceStatusResponse`

**What SiteServer's GrpcAgentProxy calls (GrpcAgentProxy.cs):**
- `client.SubmitExperimentAsync(...)` — used in `SubmitExperimentAsync`
- `client.GetRunspaceStatusAsync(...)` — used in `GetRunspaceStatusAsync`
- `client.AbortRunspaceAsync(...)` — used in `AbortRunspaceAsync`
- `PauseRunspace` / `ResumeRunspace` — NOT called by GrpcAgentProxy (no corresponding IAgentProxy methods)

**Minimum implementation:**

The Agent needs a class `AgentGrpcService` in `gRPC/Server/AgentGrpcService.cs` inheriting from `AgentControl.AgentControlBase` (the generated base class). It must override all 5 RPCs (gRPC base class is abstract — all must be overridden or build fails).

The three methods GrpcAgentProxy calls must do real work (delegate to `IRunspaceManager`). Pause/Resume can return a stub `CommandAck { Success = true }` since GrpcAgentProxy never calls them.

**Program.cs changes required:**
1. Add `builder.Services.AddGrpc();` — enables gRPC middleware
2. Add `app.MapGrpcService<AgentGrpcService>();` after `app.Build()`

**Critical: Kestrel must support HTTP/2 for gRPC.** The Agent currently sets:
```
Kestrel__Endpoints__Http__Url: http://0.0.0.0:5080
```
This is HTTP/1.1 only. gRPC requires HTTP/2. Two options:
- **Option A (recommended):** Add a second Kestrel endpoint for HTTP/2: set `Kestrel__Endpoints__Http2__Url: http://0.0.0.0:5081` and expose port 5081 for gRPC, update SiteServer's `AgentProxy__GrpcAddress` to `http://helix-agent:5081`. Clean separation.
- **Option B (simpler):** Change the existing endpoint to support HTTP/1.1 + HTTP/2 via `Protocols: Http1AndHttp2`. This serves both REST and gRPC on port 5080 with content-negotiation. Requires `Kestrel__Endpoints__Http__Protocols: Http1AndHttp2` env var in docker-compose.yml.

**Option B is simpler and lower-risk** for this closure phase. `Http1AndHttp2` is fully supported by Kestrel for cleartext (non-TLS) HTTP. The SiteServer's `GrpcChannel.ForAddress("http://helix-agent:5080")` already points at 5080, so no URL change needed.

**Does GrpcAgentProxy do health checks on startup?** No. `GrpcAgentControlClient` creates a `GrpcChannel` on construction but does not connect until an RPC is called. The channel connects lazily. SiteServer will start without error even if the Agent gRPC server is not yet up — it will only fail when an RPC is actually invoked.

**However**, `GrpcAgentControlClient` constructor creates the channel and `AgentControl.AgentControlClient` immediately. If `GrpcAddress` is unreachable, this does NOT throw at construction time (gRPC channels are lazy-connect). So the current crash-on-startup claim in the audit refers to the ConnectionStrings crash (Bug 1), not the gRPC connection failure. Bug 3 causes RPC call failures (500 responses from experiment endpoints), not SiteServer startup failure.

**Files to change:**
- `Helix.Orchestration.Agent/gRPC/Server/AgentGrpcService.cs` — new file, ~80 lines
- `Helix.Orchestration.Agent/Program.cs` — add `AddGrpc()` and `MapGrpcService<AgentGrpcService>()`
- `docker-compose.yml` `helix-agent` environment — add `Kestrel__Endpoints__Http__Protocols: Http1AndHttp2`

**Risk:** MEDIUM. gRPC on Kestrel with cleartext HTTP/2 is well-supported. The `Http1AndHttp2` protocol mode is the standard approach for development. Risk area: the `IRunspaceManager` interface — the `AgentGrpcService` must inject it correctly and the DI registration must be compatible. `IRunspaceManager` is registered as Singleton in Program.cs (line 86), so constructor injection into `AgentGrpcService` (which is also singleton-scoped via gRPC) will work without scoping conflicts.

### Bug 4 — E1/E2: SiteOverviewPage uses hardcoded static data

**Root cause (verified by direct file read):**

`helix-dashboard/src/pages/SiteOverviewPage.tsx` lines 3–10: `PLACEHOLDER_FUMEHOODS` is a module-level const array of 3 hardcoded entries. The component renders this array directly — no `useState`, no `useEffect`, no `fetch`.

**SiteServer has no `/api/fumehoods` endpoint.** Confirmed by reading all files in `Helix.Orchestration.SiteServer/Endpoints/`:
- `ExperimentEndpoints.cs` — `/api/experiments`
- `CampaignEndpoints.cs` — `/api/campaigns`
- `TrendEndpoints.cs` — `/api/trends`
- `DeviceEndpoints.cs` — `/api/devices`
- No fumehood endpoint exists.

**What data should `/api/fumehoods` return?** The `FumehoodStatus` TypeScript type (imported from `../types/dashboard`) has fields: `id`, `name`, `status` (`"running"|"idle"|"faulted"|"offline"`), `activeExperimentName?`, `lastSeenAt`.

For v0.1 scope, the SiteServer has no cross-fumehood topology database. The MQTT bridge (`MqttBridgeOptions`) has a single `FumehoodId` configured (`fh1` in docker-compose). A pragmatic v0.1 `/api/fumehoods` endpoint returns a single fumehood entry derived from the configured `FumehoodId` and the current Agent proxy status.

**Simplest correct implementation:**

SiteServer `GET /api/fumehoods`:
- Returns a list with one entry: the configured fumehood from `MqttBridgeOptions.FumehoodId`
- Status determined by querying `IAgentProxy.GetRegisteredDevices()` — if it returns devices, status is "idle" (no active experiment tracking in v0.1); if GrpcAgentProxy throws, status is "offline"
- `activeExperimentName`: null for v0.1 (no running experiment lookup)

This is sufficient for E1/E2 — the page shows a live API-driven list (not hardcoded), satisfying the "live data" requirement. Full multi-fumehood topology is out of scope for v0.1.

**Frontend changes to SiteOverviewPage.tsx:**
- Replace `PLACEHOLDER_FUMEHOODS` const with `useState<FumehoodStatus[]>([])` + `useEffect` that fetches `GET /api/fumehoods`
- Needs `baseUrl` prop (same pattern as `CampaignsPage` which takes `baseUrl: string`)
- Add loading/error state handling
- Existing `data-testid` attributes stay unchanged

**Test impact for SiteOverviewPage.test.tsx:**

Current tests (6 tests) assert on static data: "renders at least 3 fumehood cards", "shows a running status badge", "shows a faulted status badge". These will break when the data is fetched from API.

The tests must be updated to mock `fetch` and return a controlled response. The dashboard already uses this pattern in `CampaignsPage.test.tsx` (confirmed — it exists). The `SiteOverviewPage.test.tsx` tests need `vi.stubGlobal('fetch', ...)` or `vi.fn()` pattern.

**Files to change:**
- `helix-dashboard/src/pages/SiteOverviewPage.tsx` — replace hardcoded array with fetch hook
- `helix-dashboard/src/pages/SiteOverviewPage.test.tsx` — update 4 data-dependent tests to mock fetch
- `Helix.Orchestration.SiteServer/Endpoints/` — new file `FumehoodEndpoints.cs`
- `Helix.Orchestration.SiteServer/Program.cs` — add `app.MapFumehoodEndpoints()`
- `helix-dashboard/src/App.tsx` — update `SiteOverviewPage` usage to pass `baseUrl` prop (if not already done)

**Risk:** LOW-MEDIUM. The fetch pattern is established in the dashboard codebase (CampaignsPage, HistoryPage). The test update requires care — the 3 static-data assertions must become fetch-mock assertions. New SiteServer endpoint is minimal (~30 lines).

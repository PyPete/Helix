# Phase 6.3 Plan 01: Fix Execute-404 + DeviceRegistry Bridge Summary

Fixes two backend bugs that caused all manual device control calls to fail with HTTP 404, and wires `DeviceRegistry` to be populated from `CapabilityRegistry` at Agent startup.

## What Was Built

**Task 1 — Fix POST /devices/{id}/execute (C7/C9)** `112d513`

Two bugs in `DeviceEndpoints.cs` lines 136–140 caused every execute call to return HTTP 404:

- **Bug 1 (guard):** `allNames.Contains(id)` where `allNames` held full keys like `"simulator.SetFlow"` and `id` was the route segment `"simulator"`. The `Contains` check always returned false.
- **Bug 2 (invoke):** `registry.InvokeAsync(request.Capability, ...)` where `Capability = "SetFlow"` but the registry key is `"simulator.SetFlow"`.

**Fix applied:**
- Guard replaced with `registry.GetAllCapabilityNames().Any(name => string.Equals(dot > 0 ? name[..dot] : name, id, ...))`
- InvokeAsync changed to `registry.InvokeAsync($"{id}.{request.Capability}", ...)`
- `emitter?.Publish(ManualActionEvent(...))` left unchanged (uses `id` and `request.Capability` separately — correct)

**Additional correctness fixes (Rule 2 — missing attributes for correct operation):**
- Added `[FromServices]` to `SimulatorDevice? simulator` and `IRunspaceEventEmitter? emitter` parameters so minimal API parameter inference resolves them from DI rather than inferring them as body parameters. Without these attributes, `MapDeviceEndpoints()` throws `InvalidOperationException` when the types are not registered in DI.
- Made `ExecuteRequest` `public` (was `internal`). Minimal API's `RequestDelegateFactory` uses reflection to bind the body parameter at runtime; it cannot access an `internal` type from a different assembly.

**Test coverage added:** `AgentDeviceEndpointsTests.cs` — 3 tests:
1. `Execute_SimulatorSetFlow_Returns200WithSuccessTrue` — verifies HTTP 200 on happy path
2. `Execute_NonexistentDevice_Returns404` — verifies HTTP 404 with error message
3. `Execute_EmptyRegistry_Returns404` — verifies HTTP 404 when registry is empty

---

**Task 2 — Bridge CapabilityRegistry → DeviceRegistry in Program.cs (C4/C8)** `8e22a89`

`Program.cs` line 224 registered `DeviceRegistry` as an empty singleton via `AddSingleton<DeviceRegistry>()`. Nothing ever populated it, disconnecting it from `CapabilityRegistry`. `WslCompiler.ValidateDeviceBindings` resolves devices by alias from `DeviceRegistry`; with it empty, any WSL node using a `"device"` parameter would fail.

**Fix applied:** Replaced the single-line registration with a factory lambda that:
1. Resolves `CapabilityRegistry` from DI
2. Extracts unique adapter prefixes from `GetAllCapabilityNames()` (split on `"."`)
3. Registers one `DeviceDescriptor` per prefix with `prefix` as both `DeviceId` and `DeviceAlias`
4. Collects the verb-names for each prefix as the `CapabilityNames` list

**Test coverage added:** `DeviceRegistryBridgeTests.cs` — 3 pure unit tests (no web host):
1. `Bridge_SimulatorCapabilities_SimulatorDeviceIsRegistered` — verifies `TryGetDevice("simulator")` after bridge
2. `Bridge_MultipleAdapters_CorrectDeviceCountAndAliases` — verifies two devices from two adapter prefixes
3. `Bridge_EmptyCapabilityRegistry_EmptyDeviceRegistry` — verifies empty output for empty input

## Deviations from Plan

### Auto-fixed Issues (Rule 2 — missing critical functionality)

**1. [Rule 2 - Missing] Added `[FromServices]` to optional DI parameters**
- **Found during:** Task 1 RED phase test run
- **Issue:** `SimulatorDevice? simulator` and `IRunspaceEventEmitter? emitter` are optional DI services, but without the `[FromServices]` attribute ASP.NET Core's minimal API `RequestDelegateFactory` cannot determine their source when the types are absent from the DI container. This causes `InvalidOperationException: Failure to infer one or more parameters` at route registration time, preventing the entire endpoint group from starting.
- **Fix:** Added `using Microsoft.AspNetCore.Mvc;` and `[FromServices]` attribute to both parameters in `DeviceEndpoints.cs`.
- **Files modified:** `Helix.Orchestration.Agent/Api/DeviceEndpoints.cs`

**2. [Rule 2 - Missing] Made `ExecuteRequest` public**
- **Found during:** Task 1 RED phase test run
- **Issue:** `ExecuteRequest` was `internal sealed record`. ASP.NET Core's `RequestDelegateFactory` uses reflection to bind the JSON body to the parameter type. `internal` types are inaccessible via reflection from a different assembly at runtime, causing the same `InvalidOperationException`.
- **Fix:** Changed `internal sealed record ExecuteRequest` to `public sealed record ExecuteRequest`.
- **Files modified:** `Helix.Orchestration.Agent/Api/DeviceEndpoints.cs`

**3. [Rule 3 - Blocker] Switched from `WebApplication.CreateSlimBuilder()` to `WebApplication.CreateBuilder()` in test host**
- **Found during:** Task 1 RED phase build
- **Issue:** `CreateSlimBuilder()` strips full JSON body binding for minimal APIs (source-generated only). The `ExecuteRequest` body parameter could not be deserialized.
- **Fix:** Changed to `WebApplication.CreateBuilder()` in `AgentDeviceEndpointsTests.BuildAppAsync()`.
- **Files modified:** `tests/Helix.Orchestration.Agent.Tests/Api/AgentDeviceEndpointsTests.cs`

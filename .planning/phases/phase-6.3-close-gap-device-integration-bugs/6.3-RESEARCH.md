# Phase 6.3: Close Gap — Device Integration Bugs (C1, C4, C7-C9) — Research

**Researched:** 2026-06-03
**Domain:** C# ASP.NET Core Minimal API + TypeScript/React (Tauri desktop), device registry wiring
**Confidence:** HIGH — all findings are from direct source file inspection

---

## Summary

Five requirement gaps (C1, C4, C7, C8, C9) share three root causes, all localized to three files. None require architectural changes. The fixes are small and surgical.

**Root cause 1 (C1):** `DeviceRegistry.tsx` line 30 fetches `/health` and hand-crafts a phantom `{ adapterId: "agent" }` row. It must be changed to `GET /devices`, which already returns a proper `{ adapterId, capabilities }[]` array.

**Root cause 2 (C4/C8):** `Program.cs` line 224 registers `DeviceRegistry` as an empty singleton. `CapabilityRegistry` (fully populated by `DeviceAdapterExtensions.AddMigratedDeviceAdapters`) and `DeviceRegistry` (consumed by `WslCompiler.ValidateDeviceBindings`) are completely disconnected — no code copies adapter prefixes from one to the other.

**Root cause 3 (C7/C9):** `DeviceEndpoints.cs` line 137 checks `allNames.Contains(id)` where `allNames` holds full keys like `"simulator.SetFlow"` and `id` is the route segment `"simulator"`. This always fails. Additionally line 140 calls `registry.InvokeAsync(request.Capability, ...)` — this will also fail because `Capability` in the body is the verb name alone (`"SetFlow"`) while the registry key is `"simulator.SetFlow"`.

**Primary recommendation:** Fix all three in a single logical change set ordered: C7/C9 first (isolated endpoint fix), then C4/C8 (DI wiring), then C1 (frontend).

## Bug Analysis

### C1 — DeviceRegistry.tsx fetches `/health` instead of `/devices`

**Exact finding:**

`helix-desktop/src/components/DeviceRegistry.tsx` line 30:
```typescript
const res = await fetch(`${agentBaseUrl}/health`);
```

The response is plain text (`"Healthy"` / `"Degraded"`). Lines 9-18 convert it to a single synthetic `DeviceAdapter` row:
```typescript
function mapHealthToAdapters(data: { status?: string }): DeviceAdapter[] {
  return [{ adapterId: "agent", healthy: data.status === "Healthy", message: data.status ?? "Unknown", capabilities: [] }];
}
```

**What `GET /devices` actually returns:**

From `DeviceEndpoints.cs` lines 34-66 (`GET /`):
```
[{ adapterId: "simulator", capabilities: ["simulator.SetFlow", "simulator.GetFlow", ...] }, ...]
```
Each entry: `{ adapterId: string, capabilities: string[] }`. Only adapters whose first capability passes `IsAvailableAsync` are included (NullDeviceTransport always returns `true`; serial/TCP return `false` if port closed — so in dev, `simulator` will always appear).

**Type compatibility:** The existing `DeviceAdapter` interface in `agent.ts` is:
```typescript
interface DeviceAdapter { adapterId: string; healthy: boolean; message: string; capabilities: string[]; }
```
`GET /devices` returns `{ adapterId, capabilities }` — `healthy` and `message` are absent. Two options:
- (a) Map `GET /devices` response: derive `healthy = true` (it passed `IsAvailableAsync`), `message = ""`.
- (b) Update `DeviceAdapter` type to make `healthy` and `message` optional.

Option (a) is minimal-change and keeps downstream code (`d.healthy ? "Healthy" : "Unhealthy"`) valid.

**Fix:**
1. Change `fetch(${agentBaseUrl}/health)` to `fetch(${agentBaseUrl}/devices)`.
2. Replace `mapHealthToAdapters` with a function that parses `{ adapterId, capabilities }[]` and maps to `DeviceAdapter[]` with `healthy: true, message: "registered"`.
3. Parse JSON (`res.json()`) instead of `res.text()`.

**Files to change:**
- `helix-desktop/src/components/DeviceRegistry.tsx`

**Tests to update:**
- `helix-desktop/src/components/DeviceRegistry.test.tsx` — all 4 tests assume `/health` plain-text response shape. They must be rewritten to mock `GET /devices` JSON response.
- The test `"renders adapter list when fetch returns { status: 'Healthy' }"` becomes `"renders adapter list when fetch returns devices array"`.
- The `"shows 'No adapters found' when fetch returns { status: 'Degraded' }"` test becomes `"shows 'No adapters found' when fetch returns empty array []"`.

**Risk:** None. `GET /devices` is already implemented and working. No other component reads `DeviceRegistry.tsx`'s internal state.

### C4 / C8 — CapabilityRegistry → DeviceRegistry bridge is missing

**Exact finding:**

`Program.cs` line 224:
```csharp
builder.Services.AddSingleton<DeviceRegistry>();
```

`DeviceRegistry` (in `Helix.Orchestration.Core/Devices/DeviceRegistry.cs`) is a plain dictionary of `DeviceDescriptor` keyed by `DeviceAlias`. It has zero entries because nothing ever calls `registry.Register(...)` on it.

`WslCompiler.ValidateDeviceBindings` (`WslCompiler.cs` lines 169-192) iterates WSL nodes and for every node with a `"device"` or `"deviceAlias"` parameter calls `deviceRegistry.TryGetDevice(alias, out _)`. If the `DeviceRegistry` is empty, every DeviceAction node produces `WSL030 — unknown device alias`.

**What DeviceActionNode exports to WSL:**

`useHelixFlow.ts` line 133:
```typescript
parameters: { capability: `${d.adapterId}.${d.capability}`, ...d.fieldValues }
```
Note: the exported WSL node does NOT include a `"device"` parameter — it only has `"capability"` (`"simulator.SetFlow"`). So `ValidateDeviceBindings` currently skips DeviceAction nodes because they have neither `"device"` nor `"deviceAlias"` parameters.

**Re-reading the C4 evidence:** The audit says `WslCompiler.ValidateDeviceBindings rejects all DeviceAction nodes with "unknown device alias"`. However, the actual exported WSL has no `"device"` param — it has `"capability": "simulator.SetFlow"`. The C4/C8 failure path appears to be: the exported WSL compiles fine for nodes without a `"device"` param, but if a node were authored with a `"device"` param (or if the export is changed to include one), it would fail. The actual break in the workflow execution path is the `RunspaceManager` calling `capRegistry.InvokeAsync(capName, ...)` where `capName = "simulator.SetFlow"` — this works because `CapabilityRegistry` IS populated.

**Re-assessing C4/C8 root cause:**

Looking at the evidence again:
- `WslCompiler.Compile` is called in `WorkflowEndpoints.cs` via `POST /workflows/compile`.
- `WslCompiler.Compile` receives a `DeviceRegistry` parameter (line 30 of `WslCompiler.cs`).
- The `WorkflowEndpoints` resolves `DeviceRegistry` from DI — which is empty.
- If the exported WSL node uses `nodeType: "Step"` with `capability: "simulator.SetFlow"` (no `"device"` param), then `ValidateDeviceBindings` will NOT fail (it only checks nodes with `"device"` or `"deviceAlias"` params).
- If however the DeviceActionNode export puts a `"device": "simulator"` param, it would fail.

The current export (`useHelixFlow.ts` line 132-136) does NOT include `"device"`. So the compile path for the current frontend is not broken by empty `DeviceRegistry`. The audit's "C4: WslCompiler rejects DeviceAction nodes" may have been based on an older export schema or a plan that was never executed.

**Verdict on C4/C8:**
- The current WSL export from the frontend does not trigger `ValidateDeviceBindings` failures because it emits no `"device"` param.
- However, the `DeviceRegistry` singleton being empty is still a correctness issue: if any future WSL includes `"device"` params, it would fail silently.
- The phase goal says "bridge CapabilityRegistry → DeviceRegistry" is required for C4/C8.
- The minimum safe fix: in `Program.cs`, after resolving `CapabilityRegistry`, iterate `GetAllCapabilityNames()`, extract the adapter prefix, and register a `DeviceDescriptor` per unique prefix into `DeviceRegistry`.

**Exact fix for C4/C8 — bridge in Program.cs:**

Replace line 224:
```csharp
builder.Services.AddSingleton<DeviceRegistry>();
```

With:
```csharp
builder.Services.AddSingleton<DeviceRegistry>(sp =>
{
    var capRegistry = sp.GetRequiredService<CapabilityRegistry>();
    var deviceRegistry = new DeviceRegistry();
    var prefixes = capRegistry.GetAllCapabilityNames()
        .Select(name => { var dot = name.IndexOf('.'); return dot > 0 ? name[..dot] : name; })
        .Distinct(StringComparer.OrdinalIgnoreCase);

    foreach (var prefix in prefixes)
    {
        var caps = capRegistry.GetAllCapabilityNames()
            .Where(n => { var dot = n.IndexOf('.'); return string.Equals(dot > 0 ? n[..dot] : n, prefix, StringComparison.OrdinalIgnoreCase); })
            .Select(n => { var dot = n.IndexOf('.'); return dot > 0 ? n[(dot + 1)..] : n; })
            .ToList();
        deviceRegistry.Register(new DeviceDescriptor(prefix, prefix, "device", caps, new Dictionary<string, object?>()));
    }
    return deviceRegistry;
});
```

This uses `prefix` as both `DeviceId` and `DeviceAlias` — matching what `ValidateDeviceBindings` looks up.

**DI ordering risk:** `CapabilityRegistry` is registered by `AddMigratedDeviceAdapters()` (line 65), which runs before the `DeviceRegistry` registration (line 224). The factory lambda is evaluated lazily on first resolve, so ordering is not an issue as long as `CapabilityRegistry` is already registered when `DeviceRegistry` is first resolved. Confirmed safe.

**Files to change:**
- `Helix.Orchestration.Agent/Program.cs` line 224

**Tests to update / add:**
- No existing `.NET` tests for `DeviceRegistry` DI wiring in `tests/Helix.Orchestration.Agent.Tests/`.
- `WslCompilerTests.cs` already has a test for `ValidateDeviceBindings` with a populated registry — no change needed.
- New test recommended: `DeviceRegistryBridgeTests.cs` — verifies that after the bridge, `DeviceRegistry.TryGetDevice("simulator", out _)` returns `true` when `CapabilityRegistry` has `"simulator.SetFlow"` registered. This is a unit test in `tests/Helix.Orchestration.Agent.Tests/` (or `Core.Tests`).

### C7 / C9 — POST /devices/{id}/execute always returns 404

**Exact finding:**

`DeviceEndpoints.cs` lines 136-140:
```csharp
var allNames = registry.GetAllCapabilityNames().ToHashSet(StringComparer.OrdinalIgnoreCase);
if (!allNames.Contains(id))
    return Results.NotFound(new { Error = $"Device '{id}' not found." });

var invocationResult = await registry.InvokeAsync(request.Capability, request.Parameters);
```

`allNames` contains full keys: `"simulator.SetFlow"`, `"simulator.GetFlow"`, `"simulator.SetTemperature"`, etc.

`id` is the route segment, e.g. `"simulator"`.

`allNames.Contains("simulator")` is always `false` → always returns 404.

**Second bug on line 140:** Even if the guard passed, `registry.InvokeAsync(request.Capability, ...)` would be called where `request.Capability` is the verb name from the request body (e.g. `"SetFlow"`). But `CapabilityRegistry` stores keys as `"simulator.SetFlow"` — so `InvokeAsync("SetFlow", ...)` would also fail with "Capability 'SetFlow' is not registered."

**What the frontend sends:**

`DeviceManualControl.tsx` line 43:
```typescript
const res = await fetch(`${baseUrl}/devices/${deviceId}/execute`, {
  method: "POST",
  body: JSON.stringify({ capability: descriptor.verbName, parameters }),
});
```

`deviceId` is the adapter prefix (e.g. `"simulator"`). `descriptor.verbName` is the verb name alone (e.g. `"SetFlow"`).

So the route is `POST /devices/simulator/execute` and the body is `{ capability: "SetFlow", parameters: {...} }`.

**Correct fix — two lines in DeviceEndpoints.cs:**

1. Change the guard from `allNames.Contains(id)` to prefix-match:
```csharp
var adapterExists = registry.GetAllCapabilityNames()
    .Any(name => { var dot = name.IndexOf('.'); return string.Equals(dot > 0 ? name[..dot] : name, id, StringComparison.OrdinalIgnoreCase); });
if (!adapterExists)
    return Results.NotFound(new { Error = $"Device '{id}' not found." });
```

2. Change `registry.InvokeAsync(request.Capability, ...)` to use the full key:
```csharp
var fullKey = $"{id}.{request.Capability}";
var invocationResult = await registry.InvokeAsync(fullKey, request.Parameters);
```

3. Update the `ManualActionEvent` publish (line 142) — `id` and `request.Capability` are still the right fields there (the event records the adapter ID and verb separately). No change needed on the event.

**Phase 6.3 success criterion says:** `POST /devices/simulator.SetFlow/execute returns 200`. This implies the route is `POST /devices/simulator.SetFlow/execute` where `id = "simulator.SetFlow"`. This would be the FULL capability key as the route segment, not the adapter prefix.

**Reconciling with the frontend:**

If the route is meant to be `POST /devices/simulator.SetFlow/execute`, then `DeviceManualControl.tsx` must send `deviceId = "simulator.SetFlow"` not `"simulator"`. But currently `DeviceRegistry.tsx` shows buttons per `adapterId` (the adapter prefix), and `DeviceManualControl` receives `deviceId = adapterId = "simulator"`.

Two valid interpretations:

**Option A — Change the route to use the full capability key:**
- Route: `POST /devices/simulator.SetFlow/execute`
- Body: `{ capability: "SetFlow", parameters: {...} }`  (or body can be empty, capability is in route)
- This is what the phase success criterion says. Requires frontend change: `DeviceManualControl.tsx` must build URL as `${baseUrl}/devices/${deviceId}.${descriptor.verbName}/execute`.
- The `id` in the endpoint handler IS the full key. Guard becomes `allNames.Contains(id)` (already correct). InvokeAsync call becomes `registry.InvokeAsync(id, ...)` (already correct IF `request.Capability` = the verb and `id` is full key). Actually need to clarify body shape.

**Option B — Keep route as adapter prefix, fix guard + InvokeAsync:**
- Route: `POST /devices/simulator/execute`
- Body: `{ capability: "SetFlow", parameters: {...} }`
- Guard: prefix-match (described above)
- InvokeAsync: use `$"{id}.{request.Capability}"`
- No frontend change needed.

The phase success criterion `POST /devices/simulator.SetFlow/execute returns 200` is inconsistent with Option B but Option B is architecturally cleaner and requires zero frontend changes.

**Reading the audit more carefully:**

The audit evidence says: `id = 'simulator' but allNames has 'simulator.SetFlow'`. This implies the route segment `id` is the adapter prefix `"simulator"`, not the full capability key. Option B is the intended fix.

The phase success criterion `POST /devices/simulator.SetFlow/execute` appears to be poorly phrased — it likely means "POST to the execute endpoint for the simulator device's SetFlow capability" which via Option B would be `POST /devices/simulator/execute` with body `{ capability: "SetFlow" }`.

**Recommendation: Option B** — fix the guard and the InvokeAsync call. No frontend changes. The success criterion wording is a documentation artifact.

**Files to change:**
- `Helix.Orchestration.Agent/Api/DeviceEndpoints.cs` lines 136-140

**Tests to update / add:**

No existing C# tests for `DeviceEndpoints.cs` in `tests/Helix.Orchestration.Agent.Tests/`. The SiteServer has `tests/Helix.Orchestration.SiteServer.Tests/Endpoints/DeviceEndpointsTests.cs` but that covers the SiteServer, not the Agent.

New test recommended: `AgentDeviceEndpointsTests.cs` — using `WebApplicationFactory` or an in-process test host to verify:
- `POST /devices/simulator/execute` with body `{ capability: "SetFlow", parameters: {} }` returns HTTP 200 when simulator is registered.
- `POST /devices/nonexistent/execute` returns HTTP 404.

`DeviceManualControl.test.tsx` test `"clicking Execute calls POST /devices/{id}/execute with correct body"` currently verifies the URL as `http://localhost:5080/devices/device-1/execute` — this remains correct under Option B.

## Risk Assessment

### Risk 1: Option B vs success criterion wording
**Risk:** The phase success criterion says `POST /devices/simulator.SetFlow/execute returns 200`. If this is taken literally it requires the route shape to change and requires `DeviceManualControl.tsx` to construct the URL differently.
**Mitigation:** Re-read the audit evidence (`id = 'simulator' but allNames has 'simulator.SetFlow'`) — Option B (fix guard + InvokeAsync, keep route as prefix) is consistent with the audit. Plan should clarify this with a comment in the task.

### Risk 2: DeviceRegistry bridge DI ordering
**Risk:** The `CapabilityRegistry` factory (registered in `AddMigratedDeviceAdapters`) captures many device adapters including drivers that may throw on DI construction. If `CapabilityRegistry` resolution throws, `DeviceRegistry` factory lambda will also throw at startup.
**Mitigation:** This risk exists today already — if `AddMigratedDeviceAdapters` fails, the Agent can't start. No new risk introduced.

### Risk 3: WslCompiler compile path with `"device"` param
**Risk:** The current frontend export does NOT emit a `"device"` param in WSL. If future WSL includes `"device"`, `ValidateDeviceBindings` will run — but with the C4/C8 fix applied, it will resolve correctly since `DeviceRegistry` will be populated.
**Mitigation:** The C4/C8 fix future-proofs this path. No risk.

### Risk 4: DeviceRegistry.tsx — polling interval with new JSON parse
**Risk:** If `GET /devices` is slow (health checks each adapter), the 5-second poll could stack. The existing `IsAvailableAsync` check is async per adapter.
**Mitigation:** The `GET /devices` handler already has `try/catch` returning `Results.Problem`. The poll already uses `setLoading(true)` guard. No deadlock risk. The NullDeviceTransport for simulator returns immediately. Real hardware adapters may be slow but this is acceptable for a status display.

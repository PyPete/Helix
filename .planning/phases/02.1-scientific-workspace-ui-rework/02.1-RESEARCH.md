## Summary

Implement this phase as an evidence-and-boundary rework of the existing Tauri renderer, not a new scientific model or execution path. The current desktop already has five stable scientific tabs—apparatus, procedures, plans, assembly, and samples—registered in the dock layout, with Agent-backed screens that expose immutable IDs and confirmation dialogs. [VERIFIED: helix-desktop/src/shell/WorkspaceLayout.tsx:80-83,247-261] The board must become the sole primary representation over these existing read/write seams, retaining those records as the source of truth rather than inventing a canvas-local model. [HIGH: locked D-01, D-09]

The existing shell and workflow builder are integration references, not reusable authority. `HelixShell` deliberately treats desktop views as untrusted and calls native/Agent seams for lifecycle mutations; the legacy workflow builder saves JSON locally and has direct execution-oriented affordances that are not suitable as the Phase 2.1 scientific board model. [VERIFIED: helix-desktop/src/shell/HelixShell.tsx:18-18; helix-desktop/src/components/WorkflowBuilder/WorkflowBuilder.tsx:137-164; helix-desktop/src/components/ExecutionPanel/ExecutionPanel.tsx:38-38]

**Primary recommendation:** Build one independently authored `ScientificWorkspaceBoard` composition layer over the established scientific record components and read models; gate all board mutations by a single reconciliation/read-only policy, use an explicit Save/Discard/Keep-editing resolver before every context change, and accept the design only after recorded comparative and accessibility UAT. [HIGH: locked D-01, D-05-D-11]

## Architecture Patterns

### System Architecture Diagram

```text
Scientist (keyboard, pointer, screen reader)
              |
              v
Scientific Workspace Board (renderer proposal/read-model boundary)
  |-- select/inspect immutable scientific records
  |-- resolve pending draft before context change
  |-- read-only guard + persistent reconciliation strip
              |
              v
Existing authenticated native client / Local Helix Agent
  |-- Agent-backed scientific records and exact IDs
  |-- reconciliation, safety and execution evidence
              |
              v
Durable scientific evidence / execution state
```

### Recommended Project Structure

```text
helix-desktop/src/
├── components/ScientificWorkspace/ # board, inspector, draft resolver, status strip
├── components/ScientificSetup/     # retain Agent-backed record detail components
├── hooks/                           # board selection and read-only policy hooks
└── shell/                           # mount board and retain legacy baseline route
```

### Pattern 1: Single board projection over authoritative records
**What:** Use one board state that carries only selection, open detail, draft-dirty state, and displayed Agent status. Preserve IDs/revisions from `ScientificSummary`, `ScientificRevision`, `ScientificAssembly`, and sample evidence rather than converting identity into a board label. [VERIFIED: helix-desktop/src/types/scientific.ts:33-50,78-86,91-119]

**When to use:** For apparatus, procedure/plan, frozen assembly, and samples/lineage navigation. The primary representation must not preserve cards or graph as a primary-mode toggle. [HIGH: locked D-01, D-09]

### Pattern 2: Centralized interaction lock
**What:** Derive `isBoardReadOnly` once from Agent reconciliation/health/mutation uncertainty and pass it to every editable child. It must disable pointer controls, keyboard shortcuts, inspector form inputs, draft mutation actions, and board navigation that would retarget a dirty draft. [HIGH: locked D-06]

**Why:** Current individual forms only disable locally for pending/uncertain mutations—e.g., the procedure/plan form disables inputs for its local mutation state—so a board-level policy is required to prevent bypass through another panel or route. [VERIFIED: helix-desktop/src/components/ScientificSetup/ProcedurePlans.tsx:20-22,85-92]

### Pattern 3: Resolve-first context switching
**What:** Route all revision/record/procedure selection through one resolver. If the current draft is dirty, present exactly Save, Discard, and Keep editing. Save waits for an Agent result before changing context; Discard restores the existing authoritative draft; Keep editing cancels the requested navigation. [HIGH: locked D-08]

**Anti-patterns to avoid**
- **Reuse `WorkflowBuilder` as the scientific board:** it auto-exports changes and stores workflow JSON via local save/load, while the Phase 2 board must preserve immutable Agent-backed scientific records. [VERIFIED: helix-desktop/src/components/WorkflowBuilder/WorkflowBuilder.tsx:137-164]
- **A reconciliation strip with pause/hold/abort-looking controls:** its role is evidence and recovery routing only. [HIGH: locked D-07]
- **A board label as an identity substitute:** the existing sample screen explicitly distinguishes a mutable label from immutable sample ID evidence. [VERIFIED: helix-desktop/src/components/Samples/Samples.tsx:139-148]

## Common Pitfalls

### Pitfall 1: Confusing proposal, approval, frozen references, and observed execution
**What goes wrong:** A button or status text appears to start work or grant approval. **Avoid:** Ensure board vocabulary remains proposal/read-model only; show exact frozen references and observed evidence separately. [HIGH: locked D-05, D-09]

### Pitfall 2: Treating unavailable state as editable
**What goes wrong:** A health failure, held outcome, or uncertain mutation leaves alternate interactions reachable. **Avoid:** Make the board globally read-only and present the persistent strip with routes to safety/evidence/reconciliation. The existing health hook starts with `healthy: null` and reports failed native reads as unhealthy, so the board must safely handle unknown state. [VERIFIED: helix-desktop/src/hooks/useAgentHealth.ts:14-19,23-41; HIGH: locked D-06-D-07]

### Pitfall 3: Losing or retargeting a draft on selection change
**What goes wrong:** A click in board/inspector changes record context before resolving edits. **Avoid:** Put every context transition behind the same resolver, including keyboard commands and restored routes. [HIGH: locked D-08]

### Pitfall 4: Claiming the redesign is promoted from automated checks
**What goes wrong:** DOM tests or a positive preference are reported as usability approval. **Avoid:** retain legacy comparison, record task outcomes, keyboard-only and screen-reader sessions, and get explicit scientist approval. [HIGH: locked D-10-D-11]

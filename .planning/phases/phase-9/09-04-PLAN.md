    ## What is WSL?
    WSL (Workflow Specification Language) is Helix's JSON graph format for describing automated experiments. A workflow is a directed graph where each node represents an operation and edges define execution order. The Rete.js canvas in the Tauri desktop app generates WSL JSON visually.

    ## Node Types
    Write a Markdown table with columns: Node Type | Purpose | Example use:

    | Node Type | Purpose | Example Use |
    |-----------|---------|-------------|
    | Step | Executes a single device capability (e.g. SetTemperature, RunMethod) | Set reactor A to 80°C |
    | Condition | Evaluates a boolean expression on a workflow variable; routes flow to true or false edge | Check if pressure > 5 bar |
    | Branch | Routes execution to one of multiple named branches based on a condition result | Select heating vs cooling protocol |
    | Loop | Repeats a subgraph a fixed number of times | Run three wash cycles |
    | Parallel | Executes multiple branches concurrently | Start pump and heater simultaneously |
    | Delay | Waits a fixed duration before proceeding | Hold temperature for 10 minutes |
    | WaitFor | Blocks until a trend value meets a condition (e.g. temperature reaches setpoint) | Wait until temperature >= 75°C |

    ## Building a Workflow in the Desktop App
    Describe the workflow builder UI without screenshots (prose):
    1. Open the Helix desktop app and connect to your Agent (host/port on the connection screen).
    2. Navigate to the Workflow Builder tab. The canvas shows available node types in the left palette.
    3. Drag a Step node onto the canvas. In the properties panel, select a Device (e.g. vapourtec) and a Capability (e.g. SetTemperature). Fill in the parameters (reactor index, target temperature).
    4. Drag a Delay node and connect it after the Step by drawing an edge from the Step's output port to the Delay's input port.
    5. Add a WaitFor node after the Delay. Configure the trend condition (e.g. vapourtec.temperature.A >= 75).
    6. Continue adding nodes until the workflow is complete.
    7. Click "Compile" — the app sends the WSL JSON to POST /workflows/compile. The compiler returns a RunspaceDefinition or a list of diagnostics. Fix any errors reported.
    8. Once compilation succeeds, click "Execute" — the app calls POST /runspaces. The Execution Panel shows step-by-step status updates via the WebSocket stream.

    ## Compile → Execute Flow
    Include a simple Mermaid flowchart:
    flowchart TD
        A[Build workflow on canvas] --> B[Click Compile: POST /workflows/compile]
        B --> C{Compilation result}
        C -- Diagnostics --> D[Fix errors, retry]
        D --> B
        C -- RunspaceDefinition --> E[Click Execute: POST /runspaces]
        E --> F[Execution Panel shows step status via WebSocket]
        F --> G{Runspace result}
        G -- Completed --> H[View results and trend charts]
        G -- Faulted --> I[Review fault in Execution Panel]

    ## Saving and Loading Workflows
    Workflows can be saved to a local JSON file via the Workflow Library (File menu → Save Workflow). Saved files are stored in the local filesystem via Tauri's file system plugin. Load a saved workflow by choosing File → Open Workflow. The canvas is fully restored from the saved WSL JSON.

    ## Safety Interlocks
    The safety engine evaluates interlock rules on every trend update. If a limit is violated (e.g. temperature exceeds the safety envelope), the runspace is emergency-stopped automatically. The Safety Panel in the desktop app shows each rule, its current value, and whether it is in triggered or safe state.

    ## Capability Namespacing
    Capabilities in the CapabilityRegistry are namespaced by device prefix to prevent collision when multiple adapters register identically-named capabilities. Examples:
    - vapourtec.SetTemperature — SetTemperature on the VapourtecR4 adapter

    - knauer.RunMethod — RunMethod on the KnauerAzura adapter
    - systag.SetTemperature — SetTemperature on the SystagOpcUaClient adapter

    In the workflow builder, the device picker shows the prefix (device name) separately from the capability name.

    ## The Campaign → Experiment → Runspace Lifecycle
    Explain the three-level hierarchy:
    - A Campaign groups related experiments (e.g. a parameter sweep). Campaigns are created and managed via the SiteServer REST API or the React dashboard.
    - An Experiment represents one execution run within a campaign. It carries a RunspaceDefinition (compiled WSL workflow) and records the outcome.
    - A Runspace is the live execution engine on the Agent. The Agent creates a DurableRunspace when POST /runspaces is called; it tracks step-level progress and survives Agent process restart (Cleipnir PostgreSQL store).

    Include a Mermaid diagram:
    flowchart LR
        A[Create Campaign: POST /api/campaigns] --> B[Start Campaign: POST /api/campaigns/id/start]
        B --> C[SiteServer submits Experiment to Agent: POST /runspaces]
        C --> D[Agent runs DurableRunspace]
        D --> E[Step-level status via WebSocket RunspaceEvents]
        E --> F{Runspace outcome}
        F -- Completed --> G[Experiment result recorded]
        F -- Faulted --> H[Fault recorded; campaign may retry or abort]
        G --> I[Next iteration or campaign complete]

    ## Creating a Campaign
    Describe creating a campaign via the React dashboard (Site Overview → Campaigns → New Campaign). Fields: name, description, workflow definition (upload WSL JSON or select from library), iteration count. Alternatively, use the REST API: POST /api/campaigns with JSON body { "name": "...", "workflowDefinitionJson": "..." }.

    ## Starting a Campaign
    In the React dashboard, open the campaign and click Start. The SiteServer begins submitting experiments to the configured Agent. Monitor per-iteration status on the campaign page. Alternatively: POST /api/campaigns/{id}/start.

    ## Monitoring Execution
    Describe real-time monitoring: the desktop app's Execution Panel shows step status via WebSocket; the React dashboard shows live trends via /api/trends/ws (MQTT bridge from Agent). The Execution Panel updates as each step transitions from Pending → Running → Completed (or Faulted).

    ## Viewing Experiment History
    Navigate to the Experiment History page in the React dashboard. Filter by fumehood, device, or date range. Each experiment record shows the outcome (Completed/Faulted/Aborted), step count, and result summaries. Trend data is browsable in the Analytical Viewer (scalar charts, UV/MIR spectral overlay).

    ## Aborting an Experiment
    Send DELETE /api/experiments/{id} or click the Abort button in the Execution Panel. The Agent calls DurableRunspace.AbortAsync, which requests graceful shutdown of the current step. If a transport fault occurs during abort, the runspace is force-terminated and recorded as Aborted.

    ## Prerequisites
    - Docker Desktop (Windows) or Docker + Docker Compose (Linux)
    - .NET 10 SDK (for running Agent and SiteServer as dotnet run; not required if using Docker)
    - Node.js v20 (for the React dashboard and Tauri app build)

    ## Starting the Infrastructure Stack
    The root docker-compose.yml starts the supporting services (PostgreSQL, Mosquitto MQTT broker, MinIO). From the monorepo root:
      docker-compose up -d

    Default service ports: PostgreSQL 5432, Mosquitto 1883, MinIO 9000/9001.
    Default credentials (development only): PostgreSQL user helix / password helix_dev_password / database helix_orchestration.

    Note: Production hardening (TLS, credential rotation) is covered in Phase 10 deployment scripts. This guide covers local and dev deployment only.

    ## Starting the Agent
    The Agent connects to hardware devices and exposes gRPC and REST endpoints. From the monorepo root:
      dotnet run --project Helix.Orchestration.Agent

    The Agent starts on: HTTP port 5000 (REST), gRPC port 5050 (configurable via appsettings.json or ASPNETCORE_URLS env var).

    Configuration (appsettings.json or environment variables):
    - Device port names: PortName in each adapter's SerialTransportOptions (e.g. "COM3" for VapourtecR4 on Windows, "/dev/ttyUSB0" on Linux)
    - PostgreSQL connection string: ConnectionStrings__DefaultConnection
    - MQTT broker: MqttBridge__Host

    ## Starting the SiteServer
    The SiteServer aggregates Agents and serves the React dashboard API. From the monorepo root:
      dotnet run --project Helix.Orchestration.SiteServer

    The SiteServer starts on HTTP port 7020 (default dev port).

    Configure Agent connections in appsettings.json under the AgentProxy section — set UseSimulation: false and provide the Agent gRPC address for each fumehood.

    ## Standalone Mode (Desktop App Only)
    For single-fumehood operation without a SiteServer, open the Helix desktop app (helix-desktop/) and configure the Agent connection directly (host: localhost, port: 5000). The app connects to the Agent REST and WebSocket endpoints and operates without a SiteServer.

    ## React Dashboard
    Build and serve the dashboard:
      cd helix-dashboard
      npm ci
      npm run build
    Serve the dist/ directory from any static file server or point nginx/Caddy at it. The dashboard reads VITE_SITE_SERVER_URL from .env to find the SiteServer.

    ## Phase 10 Note
    Phase 10 will add a single-command setup script (setup.ps1 on Windows, setup.sh on Linux), Windows Service and systemd installers, and a hardware pre-flight check. See the Phase 10 release for the production-ready deployment path.

## Tests

### 1. Device palette appears in WorkflowBuilder
expected: Open WorkflowBuilder. A ~220px dark panel appears on the left of the canvas. While fetching it shows "Loading devices...". Once loaded, adapter names appear as collapsible section headers, each listing capability cards.
result: pass

### 2. Drag capability card onto canvas creates DeviceAction node
expected: Grab a capability card from the palette (e.g. "Set Flow") and drop it anywhere on the canvas. A new node appears at the drop position with a purple header showing "{adapterId} › {capabilityName}" (e.g. "Alicat › SetFlow"). The node body shows form fields matching the capability's parameters.
result: pass

### 3. DeviceAction parameter widgets match ParameterSchema types
expected: A DeviceAction node with a Numeric parameter shows a number input with min/max and a unit label. An Enum parameter shows a dropdown. A Boolean shows a checkbox. A String shows a text input. Hovering reveals the correct port handle colour (blue for Numeric, orange for Enum, green for Boolean, pink for String).
result: pass

### 4. Hybrid port: wired parameter hides form widget
expected: Draw an edge from any upstream node's output to one of the parameter handles on a DeviceAction node. The form field for that parameter disappears and a small "↤ wired" indicator appears in its place. Deleting the edge restores the form field.
result: pass

### 5. Export WSL serialises DeviceAction as Step
expected: Place a DeviceAction node on the canvas (e.g. Alicat › SetFlow). Click "Export WSL". The exported JSON contains a node with `nodeType: "Step"` and `parameters.capability: "Alicat.SetFlow"`. Any filled form values appear as additional parameters.
result: pass

### 6. Node border reflects live execution state (traffic-light)
expected: While the Agent is running a workflow that contains a WorkflowBuilder node: when the Agent starts executing that step, the node's border turns amber. When the step completes successfully, the border turns green. If the step faults, it turns red. Nodes not yet executed have no coloured border.
result: pass
note: Root cause diagnosed - ExecutionPanel rendered no visible status feedback. Fix applied: status badge + empty-workflow warning added to ExecutionPanel.tsx. Node borders work correctly when workflow has Step nodes.

### 7. Running node shows timing footer
expected: When a node is in the "running" state, a monospace footer appears below the node body showing elapsed time in HH:MM:SS format (e.g. "▶ 00:00:05"). If the capability declared an EstimatedDurationMs, an ETA line also appears (e.g. "ETA ~00:00:10").
result: [pending]

### 8. Completed node shows duration footer
expected: When a step completes, the node footer changes to show "✓ Finished in Xs" (or "Xm Ys" for longer durations) in green. The amber border changes to green.
result: [pending]

### 9. Faulted node shows failure footer
expected: When a step faults, the node footer shows "✗ Failed at HH:MM:SS" in red. The node border turns red.
result: [pending]

### 10. runspace-started resets all node states
expected: Starting a new runspace (clicking Run on a fresh workflow, or the Agent emitting runspace-started) resets all nodes to the idle state — no coloured borders, no timing footers.
result: [pending]

### 11. Edges animate amber dot while source node is running
expected: When a node is running, all edges leading out of that node animate with an amber moving dot. Edges from idle or completed nodes are static (no animation).
